# Workshop, the builder

Workshop is the house's only builder (WSL2, 64 threads, 125 GB of memory, a 1 TB disk). `loom build-tree` builds one future's tree there cold and puts it in the action store (builder/store.go). Kirk's rules for the machine: it keeps at least 100 GB free, runs near 80% busy, and stays reachable. This is how `build-tree` keeps them.

## Every planned future's tree (#w7agfa9)

`loom build-trees` (package `treebuilder`, unit `treebuilder/systemd/loom-build-trees.service`) runs beside `loom place`. The planner keys each future's tree where it has it checked out (`planner.ReadTreeIdentity`, the one function `build-tree` keys with) and carries the key on every test and product unit of the plan. The key is read, and the tree built, under a pinned environment (`planner.TreeBuildEnvironment`: `GOTOOLCHAIN=local`, and the runners' `GOOS=linux`, `GOARCH=amd64`), so the release is the local go's; a tree whose toolchain line (go.work's, else go.mod's) names another release, or whose units are keyed on another, isn't planned, named. `build-tree` refuses a go other than the plan's (`--go`) and a machine that isn't linux/amd64. The planner's unit, `planner/systemd/loom-plan.service`, starts it under exactly the builder's environment. The builder reads Queue's planned listing every 10 s and builds the first tree a future runs whose `trees/<key>.json` the store lacks: it checks the commit out keyless in its own clone (`~/loom-trees/adamic`, origin the public repository, no user git configuration or credential) and runs `loom build-tree --tree-key <key>` in a child, which refuses a tree keying otherwise, under every floor and bound below. One tree at a time, and one builder: its ledger, `~/loom-trees/trees.jsonl`, is flocked.

Each build is in the ledger before it starts and when it ends. Built: the index is up, and a package that didn't build is the index's to say (the change's red, or Workshop's broken). Failed: no index, Workshop's; the placer voids the future, naming why, while the failure stands, and the builder tries the tree again after 30 minutes, then an hour, and gives it up at the third failure. A tree that has failed waits behind every tree that hasn't. A checkout that fails (GitHub's 5xx, the network) is transient: retried after a minute, doubling to ten, never standing. Refused: a filesystem is under its floor, so nothing is checked out or built until it isn't. Stopped: the builder was told to stop mid-build (every update restarts it), and the next one builds it again. Interrupted: the builder died mid-build, and builds it again; a tree it died on three times is given up. A build past `--bound` (2 h) is killed with everything it started, and fails.

## The gate inputs (#8bkzf7x)

A unit runs with the gate inputs (adamic's docs/gate-inputs.md: the pinned TypeScript and cycle ledger checkouts, the CSS fixtures, the formatters' npm projects, the ignore corpus) by one name, the sha256 of their uncompressed tar. The planner reads that name from `~/.loom/gate-inputs-manifest` before every pull and puts it in every unit's key (`KeyParts.GateInputs`) and test job. A runner's `prepare.sh` fetches the manifest at `https://artifacts.loom.system.inc/gate-inputs/<name>` (the tar.gz's chunks by sha256, then `total <sha256> <bytes>` of the tar.gz and `tar <name> <bytes>`), makes room for both sizes above its 1500 MB floor before fetching anything, then fetches the chunks from beside it, checks every chunk, the total and the tar against the job's name, and unpacks them in staging beside the tree, moved into place whole. Since the name is the tar's, a Go whose gzip compresses otherwise moves no key.

`loom gate-inputs publish` (package `gateinputs`) makes them from `~/adamic-tools/gate-inputs`, the directory Workshop's env.sh names. It tars it deterministically (entries in byte order, one fixed time, no owner, modes 0644 or 0755, a hard link as its file), leaving out the cycle ledger's output and packing every git index (a checkout's, a submodule's, a worktree's) with its stat data zeroed, so the box's own test runs never move the name. When the public store already holds that name whole, it writes nothing; otherwise it writes each chunk and then the manifest under `gate-inputs/`, only what the bucket lacks, reads the manifest back from the public domain, and only then writes `~/.loom/gate-inputs-manifest`. `gate-inputs/` is under no lifecycle rule, unlike the action store's `blobs/`, where the hand-made manifest of Oct 8 expired: publish reads the bucket's lifecycle and refuses one that would reach the prefix. A key scoped to objects may not read the lifecycle, and then publish refuses too, unless `--lifecycle-unchecked` says the lifecycle was read some other way (the dashboard, a key that may). `loom gate-inputs check` reads a published manifest back as a runner would.

The name is content: the same bytes always publish to the same name, so publishing again moves no key, and any byte the tests read that changes moves every unit key, so no verdict is reused across it. The planner checks a name in the public store before keying anything on it, and again every hour, and a file naming a manifest that isn't there whole refuses the pull rather than plan units that would void at their preparation. Publish when the directory changes: when adamic's gate-input pins move (the TypeScript commit, `cloud/gate-inputs/*/package-lock.json`, the CSS fixtures' commit) or the toolchain that built them does (node). The checker archive isn't a gate input: it is each tree's own product (adamic's `TestProduct_CheckerArchive`, #nee3cfe), built from the bridge the tree compiles against, and Pack leaves a box's `checker/` out. Publishing is cheap when nothing moved, so a release hook or a daily timer may run it.

## Read sets: a unit keys the submodule files it reads (#xryaqdv)

**Off today.** The shipped planner names no `--read-sets`, so every unit keys each declared submodule's commit. They go on, `--read-sets ~/.loom/read-sets` on `loom plan` and the same on `loom build-actions` (product keys are both's), once the runners trace every unit whose key names a read set and Workshop runs `loom reads-check --key-parts` on each trace. Until then no set-keyed verdict would come back clean, so none would be reused.

A unit that declares a submodule read (a reads line naming `cohere`) keys that submodule's commit, so every cohere bump moves its key and reruns it. With read sets on and the unit measured, it keys only the paths its tests reach in the submodules: what a traced run opened, executed, stat'ed or missed, and every directory it listed. Each path resolves through the tree's tracked symlinks as the kernel resolves it, so its state is the links it went through and then the mode and object the index records where it ended (`directory` or `absent` if nothing is tracked there); a listing is its tracked names. A superproject path that resolves into a submodule (a testdata link into cohere) is the set's too. Keying is a map lookup per path, never a file read. A file the run found that the submodule doesn't track (what an install put there) names the submodule in the set, and the key holds its commit, as before read sets. A bump moves the key only when it changes one of those.

A set is recorded per code key (`planner.CodeKey`: every key part but the submodule reads, so the closure, products, superproject reads, tools, env and selection), in `units/<codeKey>.json` naming `sets/<id>.json`, under a lock. A unit's key names the set's id (`readSet`). A unit with no set (every unit whose code just changed) keys the submodules' commits: coarse, never stale. That reset isn't once: any change to a product a unit uses moves its products part and so its code key, and its set must be measured again.

**Reuse only after a clean trace.** A verdict under a key on a set is reused only once a traced run of that key came back clean (`clean/<unitKey>`). A set is measured, and a run whose reads depend on what it read (A says which B) could pass under a key whose set lacks its B; a run that read only what its key holds reads the same wherever the key agrees, so one clean trace at the key makes every verdict under it good.

**Measuring.** Trace the unit's test binary with `strace -f --decode-fds=path -e trace=<planner.TraceCalls>`, then `loom reads-check --tree <the checkout it ran in> --gate-tools <dir> --package <import path> --trace <file> --key-parts <the planned unit, as Queue posted it>`. The parser follows each process's working directory through forks, chdir and fchdir, records the file each open reached (its decoded descriptor), and leaves out what the run made itself (created, emptied, made, renamed or linked onto, removed) from the call that made it on. The command keys the unit again on the tree and refuses parts that key otherwise, checks the trace, and grows the code key's set by what the run reached. A run with no finding is recorded clean. A run on a key with a set that reached a path the set doesn't name is Loom's void: each path is a `beyondKey` finding, stderr names it, the key goes in `~/.loom/no-reuse` with why, its clean record is taken back, and the grown set moves the unit's next key. The undeclared-read check of the superproject is unchanged.

## Disk (#ckv0pmg)

- **A floor at start.** `build-tree` doesn't start while the cache base or Go's build cache has under `--floor-gb` free (100), or the temporary directory has under `--temp-floor-gb` free (20, since it may be memory). It names which one and how much it has. With `GOCACHE=off` there is no build cache to watch.
- **A floor for every job.** Admission reads the disk as its third reading, beside the CPU and memory. While a watched filesystem is under its floor, no job starts. Running jobs finish first, since one may be what is filling the disk. If none is left and the disk is still short, each job not yet started fails with the reason, so the build fails loudly instead of filling the disk or waiting forever.
- **Go's build cache under a cap.** Before a build, a cache over `--go-cache-gb` (500) loses its least recently used entries, oldest modification time first, down to three quarters of the cap. Go touches an entry it uses at most hourly, so anything used in the last 24 hours stays. Only cache entries are removed, never Go's own files, an entry used since the trim looked is left, a link at `GOCACHE` is followed, and a directory without the README go writes into its cache is refused. A lock on `loom-trim.lock` in the cache keeps two trims from overlapping.
- **Each tree's directory goes once it is up.** When the tree's index is written, the tree's working directory is renamed to `.removing-<hash>-<pid>`, a name no tree hash matches, and then emptied file by file. A removal stopped partway therefore never leaves a tree directory whose products are half gone, which buildcache would count as hits and the store would receive hollow. Before the floor is read, `build-tree` sweeps every `.removing-` directory whose process has ended, so a killed cleanup of tens of GB never keeps later builds from starting; one whose process still runs is left to it, and a file another removal took first counts as removed. A build holds a shared lock on `<base>/<hash>.lock` for its whole run, and a removal leaves a tree another build holds alone. A tree whose index didn't go up stays, so a retry needn't rebuild it. A removal that fails after the index is up is only a warning.
- **`publish.sh` on Workshop.** It runs with `LOOM_PUBLISH_FLOOR_GB=100`, the same floor; its default stays 10 for a machine that only publishes.

## Compilers

- **Go.** Warm compiles every package's tests once, then builds every main package of the tree's module and of the modules it replaces (cohere's, for adamic) with the flags adamic's `buildcache.GoBuild` uses. A product test's own go build then finds every package compiled. The 6-minute straggler of Oct 10 was the grain formatter's go build compiling the part of typescript-go's chain that only cohere's `command/cohere` reaches. A later job's go process gets a share of the compile limit (`--compile`, every thread but four by default) of max(2, limit/jobs). The jobs admitted at once are capped so their shares never add up to more than the limit.
- **C.** `build-tree` doesn't bound clang itself. The busy gauge bounds when C-heavy jobs start; a tool's count inside a running job is the tool's own business. A shim on `PATH` was tried and dropped: adamic hashes the compiler's path into its native keys, so bounding the tool that way would split keys between shimmed and unshimmed builds, and could make the same product conflict in the store. Keys must not depend on how a tool is bounded.

## For adamic's owners: a launcher for the C compiler

A bound on clang that moves no key needs adamic to run its compiler through a launcher, keeping the real compiler in its keys. Concretely, in `internal/native`:

1. **Read the launcher.** Read `ADAMIC_CC_LAUNCHER` once, as a path to an executable, or empty.
2. **Launch every compile through it.** Wherever the C compiler is run, call `exec.Command(launcher, append([]string{compiler}, arguments...)...)` when the launcher is set, and `exec.Command(compiler, arguments...)` when it isn't. That covers:
   - `tsgo.go`: the checker-archive build, `exec.Command("clang", ...)`
   - `units.go`: `compileUnit`'s preprocess and compile, and `buildUnitsWithLibrary`'s link
   - `units_tsgo.go`
   - `library.go`: the runtime library's compiles under `cachedRuntime`
3. **Probe the compiler directly.** Run `--version` on the real compiler, not through the launcher, so its output is the compiler's own.
4. **Keep the real compiler in the keys.** Leave `compiler`, the real path from `exec.LookPath(compilerName(options))` (`library.go`, `units.go:386`, `units_tsgo.go`), in `unitKey` (`units.go:280`) and `runtimeKey` (`library.go:121`). Never put the launcher's path or name there, so a launched build and an unlaunched one share every key.
5. **Leave the WebAssembly clang path as it is.** `compilerName`'s path to the clang beside `WASI_SYSROOT` stays the compiler and goes through the launcher like any other.
6. **Bound cgo separately.** cgo's compiles run `CC` and are Go's; they would be bounded by setting `CC` to a launcher script. But `buildcache.GoInputs` keys `CC` as go resolves it, so that is a separate change, with the same rule: the key names the real compiler.

With that change, `build-tree` would set `ADAMIC_CC_LAUNCHER` to a loom subcommand that takes one of a machine-wide set of slots under `~/.loom` and then runs the compiler.
